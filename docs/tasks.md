Implementation Plan: Multi‑LLM RAG SysML Diagram Generator
Phase 1: Multi-LLM Pipeline Framework
Goals:
Refactor the existing single-LLM pipeline into a 3-agent LLM pipeline (LLM1 for intent, LLM2 for diagram generation, LLM3 for validation).
Maintain current functionality (automatic generation of BDD, IBD, SMD diagrams) while introducing the new modular LLM approach.
Tasks:
Refactor Backend for Multi-Stage LLM: Update the FastAPI backend route for diagram generation to orchestrate three sequential LLM calls. The user’s request will flow through LLM1 → LLM2 → LLM3, with each stage’s output used by the next. Implement this as a pipeline within the existing async endpoint (or as internal functions called in sequence).
LLM1 – Intent Extraction: Develop a prompt template for LLM1 that instructs it to interpret the user’s natural language input and extract key intent details. LLM1 should identify:
The SysML diagram type the user is requesting or that best fits the description (e.g. BDD, IBD, or SMD).
The main system elements, relationships, or behaviors described by the user (to inform the next stage).
Format LLM1’s output in a structured way (JSON or key-value list) for easy parsing. For example: {"diagram_type": "BDD", "key_elements": ["RescueDrone", "BaseStation", ...], "summary": "..."}.
LLM2 – Diagram Generation: Design LLM2’s prompt to produce only the requested diagram in the expected JSON format. Use the output of LLM1 (diagram type and extracted details) to customize this prompt. For example, if LLM1 outputs "diagram_type": "BDD", ensure LLM2’s instructions explicitly say: “Generate a SysML Block Definition Diagram in JSON format for the following system... [including key elements from LLM1]. Do not produce other diagram types.” Incorporate any formatting cues from the current single-LLM implementation (ensuring the JSON matches the frontend’s requirements).
LLM3 – Output Validation: Create LLM3’s prompt to evaluate the diagram JSON produced by LLM2. LLM3 should check the output against the original user request and SysML standards. This includes verifying that all major aspects of the description are covered and that the JSON structure is valid for the specified diagram type (e.g., a BDD should list blocks and their relations). The current system already does a backend validity check, but LLM3 will provide a semantic check (e.g., “Did we miss any component?” or “Are any relations illogical?”). Define LLM3’s output format as a brief report or a list of issues (possibly structured, e.g., {"valid": true, "issues": [...]}).
Integrate Pipeline Logic: Handle the control flow in the FastAPI route: receive request -> call LLM1 -> parse intent -> call LLM2 -> get diagram JSON -> call LLM3 -> get validation feedback. If LLM3 reports critical issues or invalid output, decide how to handle it (e.g., log or attempt a correction cycle). On success, return the diagram JSON (and possibly any LLM3 commentary) to the frontend.
Prioritization: Implement the above in logical order: first get LLM1 and LLM2 working end-to-end (so the system can still return a diagram), then add LLM3 validation step. This ensures a usable baseline before adding the final check.
Technical Hints:
You can reuse the existing OpenAI API integration for multiple calls. Be mindful of latency – consider using efficient models (GPT-4 for the main generation, and possibly GPT-3.5 for intent or validation if speed is needed).
For parsing LLM1’s output, using a JSON format will help; you can enforce this by including a system message or few-shot example of the desired format.
Ensure that the frontend (React+TypeScript with ReactFlow) does not need major changes. It should continue to receive a JSON diagram and render it. The only change might be if we want to display LLM3’s evaluation to the user (e.g., as warnings or notes), which can be decided later.
Phase 2: RAG Integration at Each Stage
Goals:
Enhance each LLM prompt with Retrieval-Augmented Generation (RAG): inject relevant context from the knowledge base to improve accuracy and coherence.
Build a multi-level knowledge base covering general SysML and specific domain knowledge (SAR and related scenarios).
Tasks:
Expand Knowledge Base Entries: Prepare data to feed the pgvector-enabled PostgreSQL for three knowledge levels:
Level 1 – General SysML/MBSE: e.g. brief explanations of SysML diagram types and syntax, MBSE best practices. (For instance, an entry could describe what a BDD vs. an IBD represents – a BDD shows system blocks and their relationships, whereas an IBD shows internal structure
sciencedirect.com
.) Include common modeling patterns or examples for BDD, IBD, SMD.
Level 2 – SAR Domain: information specific to Search and Rescue systems. This might include typical components (e.g. rescue drones, command center, medical units), operational workflows, and any SysML models/examples of SAR missions. If available, embed a sample SAR system description and its diagram (from previous use-cases or literature) into the vector database.
Level 3 – Flight SAR & Automotive Adaptation: a specialized set of data focusing on a flight-based SAR mission and how it could map to an automotive context. For example, a description of a UAV-based search-and-rescue operation (with a SysML model of it) and a description of a Tesla/autonomous vehicle system, along with notes on integrating an autonomous car into a SAR scenario. This will help the system adapt a solution from a flight domain to an automotive domain.
Ensure each entry is stored with metadata (e.g., a domain_level tag). This can be a column in the database or part of the embedding record, so we can filter or weight retrieval results by relevance.
Implement Retrieval for Each LLM: Before calling each LLM, invoke the RAG module to fetch top-K relevant pieces of information:
For LLM1: Use the raw user query to retrieve a couple of general context items (mostly Level 1). Since LLM1’s job is intent parsing, provide it with basic SysML knowledge or definitions that might clarify terms in the input. Keep it light to avoid distracting LLM1 – e.g., if the user asks for a “state machine for a drone”, an entry about what an SMD (state machine diagram) is could be useful.
For LLM2: This is the main generation step, where detailed context helps. Use a similarity search on the vector DB with the user’s description (and possibly LLM1’s parsed info for precision). Retrieve the most relevant example diagrams or system descriptions. Ideally, get one example that matches the requested diagram type and domain. For instance, if the user is asking for a SAR system BDD, fetch the closest BDD from the SAR examples in the knowledge base. Inject this into LLM2’s prompt as a one-shot example (e.g., “Example: Description: <text> Diagram JSON: <code block>”) as was done in the previous system. This provides a template and improves output consistency.
For LLM3: Retrieve any relevant verification rules or checklists. For general SysML, this could be a list of common errors to avoid (e.g. “check that all blocks in a BDD are defined, every part in an IBD has a type”). For domain-specific checks, retrieve expectations (e.g., “In a SAR mission, ensure there is a communication link between field units and base”). Supplying LLM3 with these guidelines will help it catch domain-specific issues.
Merge Context into Prompts: Update the prompt constructors to include the retrieved context for each stage. Ensure the format clearly separates the retrieved text from instructions (you can use delimiters like ``` or quotes in the prompt). For example, LLM2’s prompt template could be: “Use the following example for reference, then generate the requested diagram…” and then include the example JSON. Similarly, LLM3’s prompt can include a bullet list of “Validation Criteria” drawn from the knowledge base before asking it to evaluate the output.
Adjust Vector Search Logic: Update the similarity search queries to use domain metadata. If LLM1 identifies or the user specifies a domain (e.g., SAR), use that to filter results (e.g., WHERE domain_level IN (1,2) for a SAR query to get general + SAR knowledge). For cross-domain queries (like the flight vs. automotive adaptation), you might combine multiple domains (e.g., get one example from flight SAR and one from automotive). Fine-tune the number of examples to avoid prompt overload – typically 1 or 2 good examples are enough.
Priority & Verification: First, make sure retrieval for LLM2 (the core generation) is working, as that has the biggest quality impact. Then add the retrieval to LLM1 and LLM3 and test them independently (you can simulate LLM1 with some sample inputs to see if the added context helps it correctly identify the diagram type). Verify that including RAG context indeed improves the outputs (compare results with and without it). The tech report’s findings suggest this greatly increases coherence.
Technical Hints:
Use pgvector’s similarity search with a cosine distance or similar metric. For example, you can use a SQL query or an ORM call that orders by embedding <-> query similarity, possibly with a filter on domain_level.
When adding new knowledge entries (like domain data), you might write a small script or migration to insert them with precomputed embeddings (using the same model as user inputs, e.g., OpenAI’s text-embedding-ada-002). This ensures consistency between how user descriptions and knowledge are represented in the vector space.
Monitor prompt length with the added context. If the prompt approaches model limits, consider truncating less relevant parts of retrieved text or using smaller examples. Quality of examples is more important than quantity.
Keep an eye on formatting: the example JSON in LLM2’s prompt should be well-formed and perhaps simplified (no unnecessary detail) so the model doesn’t confuse it with what it needs to output. LLM3’s criteria can be given as a concise list to avoid overly long prompts.
Phase 3: Domain Specialization and Adaptability
Goals:
Leverage the multi-level knowledge base to allow the system to handle domain-specific requests (especially SAR) and demonstrate domain adaptability (e.g., applying a solution from one domain to another).
Fine-tune the pipeline (prompts and retrieval) for the SAR use-case and a cross-domain example involving a Tesla (automotive) in a flight SAR scenario.
Tasks:
Domain Context Identification: Implement a mechanism to determine the domain of the user’s request. This can be explicit (e.g., user selects a domain from the UI before generation) or implicit. For implicit, use keyword matching or a small classification step: for example, if the input mentions “rescue, mission, disaster, drone” it likely falls under SAR domain (Level 2); if it mentions “Tesla, car” it might involve the automotive domain. LLM1 could also output a field like "domain": "SAR" or "domain": "Automotive" based on its interpretation. This domain info will guide which knowledge is retrieved (as set up in Phase 2).
Integrate SAR Domain Knowledge: Using the SAR-specific data added to the knowledge base, ensure the system produces richer, domain-accurate diagrams for SAR scenarios. For example, if the user requests “a BDD for a flood rescue system”, LLM2 should include domain-appropriate blocks (e.g., rescue boat, UAV, command center, etc.). The SAR knowledge base entries (Level 2) should help it do so. Test this by comparing outputs with and without SAR context. Adjust LLM2’s prompt if needed (perhaps add a line like “The system is a Search-and-Rescue mission, so include relevant components such as...”).
Flight SAR Example (Level 3) Usage: Ensure that the detailed flight-based SAR mission example is effectively utilized. For instance, if the user’s request is similar to that example (e.g., “diagram of an aerial search mission using drones”), the retrieval should pull that example, and LLM2 should closely follow its structure. This will validate that our one-shot example approach works in a specific domain scenario. LLM3 can also use this example (or related rules) to validate completeness (e.g., the example might list required subsystems; LLM3 can check the generated output against that list).
Automotive/Tesla Adaptation Case: Develop a test case (and supporting knowledge data) where an automotive system is used in a SAR context. For example, consider a prompt: “Generate an Internal Block Diagram for a search-and-rescue operation where a Tesla vehicle is used as a responder.” In this case, the system should combine Level 2 SAR knowledge (what components a responder system needs) with Level 3 automotive knowledge (Tesla’s capabilities like sensors, Autopilot, energy supply). To support this, ensure the Tesla/autonomous car entry is in the vector DB and will be retrieved for such a query. You might need to tweak the similarity search (the query embedding might not naturally pull an automotive entry for a SAR query unless there are overlapping terms). One approach: if LLM1 detects multiple domains (both “SAR” and “Automotive”), perform two searches and merge the context (one result from SAR, one from automotive). Then instruct LLM2 to integrate both: e.g., “In the example, a UAV is used for search. Now, instead, incorporate an autonomous car (Tesla) to perform a similar role on the ground.”
Validation and Iteration: Utilize LLM3 heavily in this phase to evaluate the domain-specific outputs. If LLM3 notes, for example, “The diagram is missing a communication link that is present in the example” or “The Tesla’s role is unclear”, use that feedback to refine prompts or add more info to the knowledge base. We might iterate: update the prompt to explicitly ask for a certain component if LLM3 consistently finds it missing, or add additional training info (few-shot) for those cases.
Frontend/UI Updates: If not done in Phase 2, add UI elements to support domain and diagram-type specification. For instance, a dropdown for “Domain” (General vs SAR, etc.) and “Diagram Type” (auto-detect or manual selection of BDD/IBD/SMD). This gives power users more control and helps testing. Ensure these selections are passed to the backend (e.g., as query params or in the JSON payload). The backend can then use them (overriding LLM1’s guess if user explicitly chooses).
Priority: Focus first on getting robust SAR domain performance (as that’s the main use-case driving this project). Next, tackle the cross-domain adaptation example, as it is a bit more experimental. The system should be demonstrably better at SAR diagrams by the end of this phase, and capable of handling the Tesla-in-SAR scenario in at least a basic way (even if the output isn’t perfect, it should sensibly include elements from both domains).
Technical Hints:
For domain detection, a simple approach is fine (even hard-coding keyword triggers). Given time constraints (2–3 weeks total), implementing a full ML classifier for domain might be overkill; using LLM1 or rules will suffice.
Keep the domain-specific example data small and focused. It’s better to have a few high-quality, representative examples than many irrelevant ones. For instance, one good BDD of a SAR system and one IBD of a Tesla’s systems can go a long way when combined.
When combining context from multiple domains, clearly segregate them in the prompt (e.g., “Example A: [Flight SAR system] … Example B: [Automotive system] … Now generate the new diagram…”). This helps the model understand the connection.
Test various phrasing of user requests (especially for the adaptation case) to ensure the system is robust to different wordings. You may discover the prompt needs slight adjustments after testing (common in prompt engineering).
Phase 4: Final Integration and Documentation
Goals:
Polish the implementation for reliability, optimize where possible, and document the new architecture and usage for future maintainers.
Conduct end-to-end testing and make any final adjustments before deployment.
Tasks:
Robustness Improvements: Add error handling and fallback logic around the LLM calls. For example, if LLM1 returns an unstructured or incomplete response, implement a simple retry or default to a reasonable assumption (default to BDD perhaps). If LLM2’s JSON is invalid (cannot be parsed), log the error and attempt a second pass (maybe by gently formatting the prompt or using a smaller temperature). Leverage the existing validation logic that was in place for the single-LLM approach – this can catch JSON errors or missing fields and could even be used to prompt LLM3 or LLM2 to fix the issues (possibly in a future iteration).
Performance Tuning: With 3 LLM calls and RAG, latency might increase. Profile the end-to-end time and see if any stage is a bottleneck. Some optimizations to consider: caching LLM1 results for identical/similar queries, or even skipping LLM1 if the user explicitly chose a diagram type (saving one API call). Ensure that vector searches are using indexes properly (pgvector queries are usually fast if indexed; consider adding an index on domain_level if it significantly narrows searches). Also verify that adding the domain filter in queries doesn’t drastically reduce recall (it should not if data is well-tagged).
Finalize Frontend Integration: Make sure the frontend properly handles any new inputs or outputs. For instance, if we added a domain selector or if LLM3’s feedback is to be shown, implement those UI elements. If showing LLM3 feedback, format it nicely (e.g., a list of suggestions or a simple “Quality: Good/Needs Review” status). This is optional, but could be useful for user trust.
Documentation: Write a clear README or developer document outlining how the new system works. This should include:
An updated architecture diagram or description, showing the 3 LLM agents in the flow (maybe draw a simple block diagram depicting User Input -> LLM1 -> LLM2 -> LLM3 -> Diagram).
Description of the knowledge base contents and how to update or add to it (e.g., how to add a new domain or new examples – mention any scripts or SQL needed to insert embeddings).
Instructions on configuration changes, like any new environment variables (for instance, if we use separate API keys or model IDs for different LLMs, or flags for domain mode).
Usage guide for users (if they need to select domain or if the system auto-detects, explain how to get the best results).
Testing & QA: Before concluding, test the entire system in a fresh environment (e.g., run the Docker Compose setup to ensure nothing was broken by the changes). Write a few unit tests or integration tests if time permits: for example, a test that sends a known input and checks that the output JSON includes certain expected blocks (this could be as simple as using requests to hit the API and then assertions in Python). This will help catch regressions.
Team Demo and Feedback: Present the upgraded system to the team or stakeholders. Collect feedback especially on the quality of diagrams in the SAR domain and the usefulness of LLM3’s validation. There may be quick tweaks from this feedback (e.g., adjusting a prompt wording that was confusing the model, or adding another example to the knowledge base to cover a missed case). Tackle any high-priority fixes that come out of this review.
Technical Hints:
Given the short timeline, favor improvements that yield the most benefit for effort. For example, prompt tuning and adding high-quality examples can often boost performance more than complex coding changes.
If certain advanced features (like fully automatic domain detection or multi-domain blending) are not fully achieved, document their partial implementation and potential next steps. It’s okay to note areas for future work in the documentation. This plan sets up a foundation that can be extended, so clarifying those extension points is useful.
Use version control (Git) effectively during this process: keep each phase or major feature in separate commits or branches. This will make it easier to revert or identify issues introduced at each stage.
Leverage the developer’s knowledge of the stack: for instance, use FastAPI dependency injection or events if needed to preload the knowledge base into memory on startup (to avoid repeated DB calls for static data). Similarly, ensure the React frontend is built and served correctly via the existing Docker setup (update Dockerfiles if new dependencies were added, like any new Python libraries for embeddings or data processing).
By following these phases, the system will evolve from a single-LLM prototype into a robust multi-LLM solution with rich domain knowledge integration. Each phase delivers a working increment (from basic pipeline, to improved accuracy with RAG, to specialized domain support, and finally a polished product), suitable for the 2–3 week development timeline.
